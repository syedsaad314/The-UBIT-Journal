WEEK 01

Introduction to Requirements Engineering & Classification of Requirements

1.1 What is Requirements Engineering (RE)?

Requirements Engineering is the process of finding out, analyzing, documenting, and checking the services a system should provide and the constraints under which it must operate.

In simple words: Before you build a system, you must clearly understand WHAT it needs to do, WHO will use it, and WHAT rules it must follow. That whole process = Requirements Engineering.

Services Constraints Stakeholders Feasibility Documentation

Why RE matters so much:

  • Studies show that most software failures are due to poor or missing requirements, NOT bad coding.
  • Fixing a requirements error AFTER development costs 100x more than fixing it during RE.
  • Requirements are the foundation — if the foundation is wrong, everything built on it collapses.

1.2 What is a Requirement?

A requirement is a description of what a system should do OR a constraint on how it should operate. It can range from:

  • High-level abstract statement: "The system should manage patient records."
  • Detailed formal definition: "The system shall store patient records with a unique 8-digit ID and allow search by name within 2 seconds."

1.3 Classification of Requirements

A) Functional Requirements

These describe what the system should DO — the services, behaviors, and functions the system must provide.

Examples (Mentcare System):

  • A user shall be able to search the appointments list for all clinics.
  • The system shall generate a daily list of patients for each clinic.
  • Each staff member shall be identified by an 8-digit employee number.

MCQ 1

Which of the following BEST defines a non-functional requirement?

A. A description of what function the system must perform
B. A constraint on how the system should provide its services

User requirements are for non-technical stakeholders (managers, clients) so they must use simple natural language, easy diagrams, and tables — not technical notations.

B. Consistency

Consistency means no two requirements contradict each other. Completeness means all needed services are defined.

Short Questions
SQ 1

Differentiate between functional and non-functional requirements with one example each.

Answer

Functional Requirements describe what the system should DO — specific behaviors, functions, and services. Example: "The system shall allow users to search patient records by name."

Non-Functional Requirements describe HOW WELL the system performs — constraints on quality, performance, and process. Example: "The system shall respond to any search query within 2 seconds."

Key difference: Functional = functionality. Non-functional = quality/constraint. NFRs often affect the entire system, not just one component.

SQ 2

What is a Domain Requirement? Why are they difficult to manage?

Answer

Domain requirements come from the application domain (industry-specific rules) rather than user needs. Example: "Train braking distance must be calculated using the ISO safety formula."

They are difficult because: (1) Software engineers may not understand the domain deeply. (2) Domain experts use specialized jargon. (3) If a domain requirement is missed, the system may be legally non-compliant or unsafe.

SQ 3

Why is it important to write NFRs quantitatively? Give an example.

Answer

Quantitative NFRs are measurable and can be objectively tested, preventing disputes between client and developer.

Bad (qualitative): "The system should be easy to use."
Good (quantitative): "Medical staff shall use all system functions after 2 hours of training, with no more than 2 errors per hour."

The good version can actually be tested and verified — the bad version cannot.

SQ 4

What are stakeholders? Give 4 examples from a hospital system.

Answer

Stakeholders are anyone who is affected by the system or has a legitimate interest in it. In the Mentcare (hospital) system, stakeholders include:

  • Patients (whose data is stored)
  • Doctors (who use the system for patient care)
  • Nurses (who coordinate appointments)
  • IT staff (who maintain the system)
  • Medical ethics manager (ensures legal/ethical compliance)

Each stakeholder has different needs, which can sometimes conflict with each other.

Situation-Based Questions
SITUATION 1
Scenario: A team is building an online banking system. The client says "The system should be fast, secure, and easy to use." A junior developer says these are all functional requirements. The senior developer disagrees.

Who is correct? Classify each statement and explain.

Answer

The senior developer is correct. "Fast," "secure," and "easy to use" are all Non-Functional Requirements (NFRs), not functional requirements.

  • Fast → Performance NFR. Should be specified as: "Response time ≤ 3 seconds for any transaction."
  • Secure → Security NFR. Should be: "All data must be encrypted using AES-256. No unauthorized access permitted."
  • Easy to use → Usability NFR. Should be: "New users complete first transaction within 10 minutes without help."

The client's statements are goals, not requirements. They must be rewritten quantitatively to become proper NFRs.

SITUATION 2
Scenario: A university is developing a student portal. Different stakeholders have given these requirements: The Registrar says "Students must not see other students' grades." The IT Head says "The system must run on all browsers." The Dean says "Students can see their full transcript." A developer notices these may conflict.

Identify the requirements type for each, and explain the conflict.

Answer
  • Registrar's requirement: Security NFR (privacy/external requirement)
  • IT Head's requirement: Product/technical NFR (portability)
  • Dean's requirement: Functional requirement

Conflict: "Students cannot see other students' grades" vs. "Students can see their full transcript" — these could conflict if "full transcript" is interpreted to include grade comparisons or if system access controls are poorly designed.

This is a classic stakeholder requirements conflict that must be resolved through requirements negotiation — all parties meet and agree on a compromise (e.g., students see ONLY their own full transcript).

WEEK 02

Requirements Process, Levels/Layers of Requirements & Requirement Characteristics

2.1 The Requirements Engineering Process

RE is NOT a simple linear process — it is iterative and spiral. Requirements keep evolving as understanding grows.

📐 The Spiral View of RE Process (Sommerville Fig 4.6)
Requirements Specification _______________ / \ / System reqs \ / specification \ / and modeling \ / ──────────────────── \ / User reqs specification \ / ──────────────────────── \ / Business reqs specification \ ● ─────────────────────────────── ● → System Start Requirements │ Requirements │ System Document │ Elicitation │ req. │ │ elicitation │ Feasibility │ │ study │ User reqs │ │ elicitation \_____________/ Requirements Validation (Prototyping + Reviews)

The three core RE activities, always interleaved:

  1. Elicitation & Analysis: Discovering requirements by interacting with stakeholders
  2. Specification: Converting requirements into a standard, documented form
  3. Validation: Checking that requirements define the system the customer actually wants

2.2 Levels / Layers of Requirements

Requirements exist at different levels of abstraction. Understanding which level you're at is crucial:

📐 Levels / Layers of Requirements
┌──────────────────────────────────────────────────────────┐ │ BUSINESS REQUIREMENTS │ │ (Why the system is needed — Business goals/objectives) │ │ "The hospital needs to reduce patient wait times by 30%" │ └──────────────────────────┬───────────────────────────────┘ ↓ ┌──────────────────────────────────────────────────────────┐ │ USER REQUIREMENTS │ │ (What users need to do — their tasks and goals) │ │ "Receptionist must schedule appointments quickly" │ └──────────────────────────┬───────────────────────────────┘ ↓ ┌──────────────────────────────────────────────────────────┐ │ SYSTEM REQUIREMENTS │ │ (What the system must do — detailed technical specs) │ │ "System shall allow appointment booking in ≤ 3 clicks" │ └──────────────────────────┬───────────────────────────────┘ ↓ ┌──────────────────────────────────────────────────────────┐ │ SOFTWARE DESIGN SPECIFICATION │ │ (How the system will do it — design decisions) │ │ "Use calendar API, database schema: appointment(id, │ │ patient_id, doctor_id, date, time, status)" │ └──────────────────────────────────────────────────────────┘

Important Rule: Requirements should tell us WHAT the system does, NOT HOW it does it. Architecture/design comes later.

2.4 Analyzing Quality Requirements

Quality requirements are essentially NFRs — they define HOW GOOD the system must be. Analyzing them involves:

  1. Identify the quality attribute: Performance? Security? Reliability?
  2. Make it quantitative: Express with measurable metrics
  3. Check for conflicts: Security vs. Performance often conflict
  4. Prioritize: Not all quality attributes can be maximized simultaneously
  5. Validate with stakeholders: Confirm the numbers are realistic and acceptable

A. Completeness
B. Verifiability (and Unambiguousness)

Short Questions
SQ 1

Explain the spiral view of the Requirements Engineering process.

Answer

The spiral model of RE shows that requirements engineering is not a simple linear process but an iterative one. The activities — elicitation, specification, and validation — are organized in a spiral where each loop represents one cycle of increasing detail and understanding.

Early loops focus on high-level business and user requirements. Later loops dive into detailed system requirements. The output at the center is the System Requirements Document. This model allows requirements to evolve as stakeholder understanding improves.

SQ 2

List and briefly explain 5 characteristics of good requirements.

Answer
  • Complete: All necessary information is included, nothing is missing.
  • Unambiguous: Has exactly one clear interpretation — no vagueness.
  • Consistent: No contradictions between requirements.
  • Verifiable: Can be tested with objective methods or measurements.
  • Traceable: Can be traced back to its source — which stakeholder or document required it.
Situation-Based Questions
SITUATION 1
Scenario: A startup is building an e-commerce app. The CEO says "We need a fast, beautiful app that customers love." The Product Manager writes these requirements: 1) App should look good. 2) Loading should be fast. 3) Customers should be happy. The developer complains these requirements are useless.

Evaluate each requirement against the characteristics of good requirements and rewrite them properly.

Answer

All three requirements are bad requirements. Here's the analysis:

  • Req 1 "App should look good": Fails Unambiguousness (what is "good"?) and Verifiability (cannot be tested). Rewrite: "App UI must follow company brand guidelines. User satisfaction score ≥ 4/5 in usability testing."
  • Req 2 "Loading should be fast": Fails Verifiability (how fast?). Rewrite: "App loads fully within 3 seconds on a 4G connection."
  • Req 3 "Customers should be happy": Fails Completeness, Verifiability, and Unambiguousness. Rewrite: "Monthly active user retention rate ≥ 70% after first month."

The developer is correct — requirements must be testable, measurable, and precise to be useful.

3.1 Software Requirements in the Context of Systems Engineering

Software rarely exists alone. It is usually part of a larger system that includes hardware, people, processes, and organizations. Understanding this context is essential.

  • Interface requirements: How the software must interface with hardware, other software, and users
  • Operational requirements: The environment in which the software will run

3.3 Requirement Traceability

Requirement traceability means being able to track every requirement from its origin through development to the final system. It answers: WHERE did this requirement come from? WHAT design components implement it? WHAT tests verify it?

📐 Requirement Traceability Matrix (RTM)
┌─────────────────────────────────────────────────────────────────┐ │ REQUIREMENT TRACEABILITY MATRIX │ ├──────┬────────────────┬──────────┬───────────┬────────────────┐ │ REQ# │ DESCRIPTION │ SOURCE │ DESIGN │ TEST CASE │ ├──────┼────────────────┼──────────┼───────────┼────────────────┤ │ R001 │ User login │ Sec.Mgr │ Module-A │ TC-001, TC-002 │ │ R002 │ Search patient │ Doctor │ Module-B │ TC-003 │ │ R003 │ Generate report│ Manager │ Module-C │ TC-004, TC-005 │ │ R004 │ Data encrypt │ IT/Legal │ Module-D │ TC-006 │ └──────┴────────────────┴──────────┴───────────┴────────────────┘ TRACEABILITY LINKS: ┌──────────────┐ ┌──────────────┐ ┌──────────────┐ │ STAKEHOLDER │────►│ REQUIREMENT │────►│ DESIGN COMP │ │ (Source) │ │ │────►│ TEST CASE │ └──────────────┘ └──────────────┘ └──────────────┘ ↑ │ └────────────────────────────────────────┘ (Backward Traceability)

Two Types of Traceability:

  • Forward Traceability: From requirements → design → code → tests (tracking implementation)
  • Backward Traceability: From design/tests back to the original requirement or stakeholder (tracking origin)

Why Traceability Matters:

  • When a requirement changes, traceability tells you WHAT ELSE is affected (impact analysis)
  • Ensures ALL requirements are implemented — nothing is missed
  • Helps verify that the final system meets all original requirements
  • Required for safety-critical and regulated systems (medical, aviation, defense)

Short Questions
SQ 1

What is requirement traceability and why is it important?

Answer

Requirement traceability is the ability to track every requirement from its origin (stakeholder/business goal) through the development process to design, code, and test cases, and back again.

Importance:

  • Enables impact analysis — when a requirement changes, you know what else is affected
  • Ensures all requirements are implemented (nothing missed)
  • Proves the system meets what was originally required
  • Essential for safety-critical systems (aviation, medical, nuclear)

Tool used: Requirement Traceability Matrix (RTM) that maps Req# → Source → Design Component → Test Case.

SQ 2

Why is software development considered to address "wicked problems"?

Answer

Sommerville uses the term "wicked problems" for problems that cannot be completely defined upfront. They have no definitive solution and the full understanding of the problem only emerges as you work on it.

For software, this means: the requirements are inherently incomplete when first gathered, because users don't fully know what they want until they see a working system. New requirements emerge, old ones change, and the business environment itself shifts during development. This is WHY requirements always evolve.

SQ 3

How does systems engineering context affect software requirements?

Answer

In systems engineering, software is part of a larger sociotechnical system that includes hardware, people, and organizational processes. This means:

  • Software requirements must account for interfaces with hardware components
  • Requirements from higher-level system design are "allocated" to software
  • Changes in hardware or processes may force changes in software requirements
  • Software cannot be fully specified without understanding the complete system context

Example: A hospital software system's requirements depend on what sensors are available, what the nurses' workflow is, and what data regulations apply — not just what the software itself should do.

Situation-Based Questions
SITUATION 1
Scenario: A government agency built a tax-filing software. After 2 years, the government changed tax laws, the agency got new hardware servers, and users complained the mobile interface was added as an afterthought. The requirements document from Year 1 is now completely outdated and nobody knows which design components relate to which requirement.

Identify the requirement evolution issues, classify the changed requirements, and explain what traceability mechanisms should have been in place.

Answer

Issues identified:

  • Tax law changes → Volatile requirements (external regulatory requirements that changed)
  • New hardware servers → Consequential requirements (new technical requirements due to infrastructure change)
  • Mobile interface → Emergent requirements (discovered after deployment)

What should have been in place:

  • A Requirement Traceability Matrix (RTM) mapping each requirement to its source, design component, and test case
  • A change management process to evaluate impact of tax law changes before implementation
  • Unique IDs for each requirement to track changes over time
  • Separate classification of volatile vs. enduring requirements so volatile ones get extra attention

Without traceability, when tax law changed, the team couldn't identify which requirements, design components, and test cases needed updating — causing massive rework.

WEEK 04

Requirement Prioritization & Trade-off Analysis

4.1 Requirement Prioritization

When resources (time, money, people) are limited, you can't implement ALL requirements at once. Prioritization decides WHICH requirements to implement FIRST.

Why Prioritize?

  • Resources (time, money, team) are always limited
  • Some requirements are critical; others are "nice to have"
  • Helps manage stakeholder conflicts — when two stakeholders want different things, priority resolves disputes
  • Essential for iterative/agile development (what goes in Sprint 1?)

Prioritization Techniques:

📐 MoSCoW Prioritization Method
┌─────────────────────────────────────────────────────────────┐ │ MoSCoW METHOD │ │ │ │ M — MUST HAVE (Critical, system fails without it) │ │ "The system MUST authenticate users" │ │ │ │ S — SHOULD HAVE (Important but not critical) │ │ "The system SHOULD generate PDF reports" │ │ │ │ C — COULD HAVE (Nice to have, low priority) │ │ "The system COULD have dark mode" │ │ │ │ W — WON'T HAVE (Not for this version, maybe later) │ │ "The system WON'T have AI chatbot in v1.0" │ │ │ │ ⚠️ Start with MUST, then SHOULD, then COULD │ └─────────────────────────────────────────────────────────────┘

4.2 Trade-off Analysis

Trade-off analysis means evaluating competing options or conflicting requirements to find the best balance. When you can't have everything, what do you choose?

Steps in Trade-off Analysis:

  1. Identify the conflict: Which requirements or quality attributes are competing?
  2. Define evaluation criteria: Cost, risk, performance impact, user value
  3. Analyze options: What are the consequences of choosing each option?
  4. Involve stakeholders: Who is affected? Their input is essential
  5. Make and document the decision: Record WHY you chose this trade-off
  6. Review: As the project progresses, re-evaluate if the trade-off is still valid
🧠 Memory Trick

MoSCoW = Must · Should · Could · Won't — use this in any exam question about prioritization.
Trade-off mantra: Every gain has a cost. Security costs performance. More features cost time. More reliability costs money. Always explain BOTH sides.

Short Questions
SQ 1

What is the Requirements Change Management process? Explain each step.

Answer

The Requirements Change Management process (Sommerville) has three main stages:

  • 1. Problem Analysis & Change Specification: The identified problem or change request is analyzed. The requester clarifies the problem. A specific change proposal is formulated. If the problem is invalid, it's rejected here.
  • 2. Change Analysis & Costing: The proposed change's effects are assessed using traceability information. What requirements, design, and code will be affected? What is the estimated cost and time? Based on this, a decision is made whether to proceed.
  • 3. Change Implementation: If approved, the requirements document, design, and code are updated. The system is retested. The requirements document should be updated BEFORE or immediately with the system change — never after, as they will get out of sync.
SQ 2

What is "scope creep" and how does proper requirements management prevent it?

Answer

Scope creep is the uncontrolled, gradual expansion of project scope through unauthorized or informal requirement additions without corresponding adjustments to budget, schedule, or resources.

Requirements management prevents it through: (1) Formal change control — all changes must go through the change management process. (2) Impact analysis — every change is evaluated for cost/schedule impact before approval. (3) Unique requirement IDs — every change is tracked. (4) Stakeholder approval — changes are approved by authorized stakeholders, not just requested informally.

  • Business environment changes during the process

Short Questions
SQ 1

Explain the interaction between requirements and system architecture.

Answer

Requirements and architecture have a bidirectional relationship:

  • Requirements → Architecture: NFRs especially drive architectural choices. A requirement for 99.9% availability leads to a redundant, fault-tolerant architecture. A security requirement leads to security layers in the design.
  • Architecture → Requirements: The chosen architecture constrains requirements. If a legacy system uses a certain database, new requirements must be compatible with it. Architecture decisions may generate new requirements.

Although ideally requirements come first, in practice they co-evolve. Sommerville notes that architectural design information sometimes appears in requirements documents because: (1) Initial architecture helps structure requirements, (2) Interoperability with existing systems constrains design, (3) External regulators may mandate specific architectures.

SQ 2

What are the main challenges in requirements elicitation?

Answer
  • Stakeholder uncertainty: Users often don't know what they want until they see it
  • Domain jargon: Stakeholders use technical domain terms that RE engineers may not understand
  • Conflicting requirements: Different stakeholders have different needs that may contradict each other
  • Political factors: Managers may request requirements to increase their organizational influence, not for genuine system need
  • Dynamic environment: Business conditions change during elicitation, making requirements obsolete
  • Tacit knowledge: Experts don't mention things they consider "obvious" — yet engineers don't know them
Situation-Based Questions
SITUATION 1
Scenario: A team is building a real-time stock trading platform. The requirement says "System must be fast." The architect proposes using a simple relational database with standard server. Later, performance testing shows the system can only handle 50 transactions/second but the requirement (now clarified) is 10,000/second. The architect says "You should have told me this earlier — my entire design would have been different."

Explain the relationship between this NFR and the architectural decision, and what should have been done differently.

Answer

Problem: The NFR "fast" was not properly specified quantitatively. Had it been written as "10,000 transactions/second," the architect would have immediately known a standard relational DB was insufficient.

Requirements → Architecture impact: A 10,000 TPS requirement would have driven a completely different architecture: in-memory databases (Redis), distributed computing, message queues (Kafka), load balancers, and horizontal scaling — none of which were in the current design.

What should have been done:

  • NFR written quantitatively: "System shall process minimum 10,000 transactions per second"
  • Early architectural review with these NFRs before any design started
  • The architect and RE team should collaborate at requirements stage to validate feasibility
  • Prototype/benchmark test with a small architecture spike to validate performance NFR

This illustrates why "fast" is a terrible requirement — and why architecture and requirements must be reviewed together.

Short Questions
SQ 1

List and explain the 5 types of checks performed during requirements validation.

Answer
  • 1. Validity Checks: Ensure requirements still reflect actual user needs. Circumstances may have changed since requirements were first gathered.
  • 2. Consistency Checks: Ensure no two requirements contradict each other. No conflicting constraints or duplicate descriptions of the same function.
  • 3. Completeness Checks: Ensure all functions and constraints needed by the user are included. Nothing is missing — all exceptions and edge cases covered.
  • 4. Realism Checks: Ensure requirements can actually be implemented within the available budget and schedule using current technology.
  • 5. Verifiability: Ensure each requirement can be tested objectively. A requirement you cannot test is dangerous — you can never prove the system meets it.
SQ 2

Why is prototyping useful in requirements validation?

Answer

Prototyping builds an executable model of the system that stakeholders can actually interact with. It is valuable because:

  • People find it much easier to react to a working prototype than to read abstract requirements
  • Stakeholders can discover missing or incorrect requirements by experiencing the prototype
  • Misunderstandings become immediately visible when users interact with the system
  • It reduces the risk of building the wrong system — errors are caught cheaply during requirements rather than after development

Prototyping can be combined with ethnography — ethnographic observations inform the prototype, which then focuses further observations.

Answer

Use it for: Large enterprise systems, safety-critical systems (medical, aerospace, defense), outsourced projects with hundreds or thousands of requirements. For small projects, a shared spreadsheet or wiki is sufficient.

Short Questions
SQ 1

Explain "requirements creep" and "gold-plating." How are they different and how can both be controlled?

Answer

Requirements creep: Uncontrolled expansion of scope by adding new requirements from stakeholders without corresponding changes to budget, schedule, or resources. Comes from the CLIENT/stakeholder side.

Gold-plating: Adding unnecessary features, functions, or technical complexity beyond what the requirements specify. Comes from the DEVELOPER side — developers "improve" the system beyond what was asked.

How to control both:

  • Formal change management process — all changes (from any source) must be evaluated and approved
  • Clear, unambiguous requirements — if requirements are precise, both clients and developers know exactly what is needed
  • Regular reviews — compare what is being built against the approved requirements
  • Requirements ownership — each requirement has a named owner who approves changes
SQ 2

What special challenges arise in managing requirements when software is acquired from an external supplier?

Answer
  • Contractual precision: Requirements become part of a legal contract — every ambiguity can cause expensive disputes
  • Change cost: Each requirement change requires a formal contract amendment, which is expensive and time-consuming
  • Interpretation risk: Supplier may interpret requirements differently from what the acquisition org intended
  • Verification challenge: Acquisition org must verify that supplier built exactly what was required — needs strong traceability
  • Communication distance: Supplier may be in a different location/country — misunderstandings accumulate over time

Solutions: Very precise SRS, formal requirements reviews, regular milestone reviews, third-party independent verification, mandatory traceability documentation from supplier.

SITUATION 1

Answer

In acquisition contexts, informal requirement additions without contract amendments leave the developer with no legal protection.

Requirements Engineering for Agile Methods

13.1 Agile RE vs. Traditional RE

Traditional RE (waterfall-style) produces a complete requirements document BEFORE development. Agile RE accepts that requirements will evolve and develops them incrementally alongside the code.

📐 Traditional vs. Agile Requirements Approach
TRADITIONAL (Plan-Based): ───────────────────────────────────────────────────────── Requirements → Design → Code → Test → Deploy (Complete SRS before anything else is built) AGILE (Incremental): ───────────────────────────────────────────────────────── Sprint 1: Elicit a few requirements → Design → Code → Test → RELEASE small increment Sprint 2: Elicit more requirements → Design → Code → Test → RELEASE Sprint 3: ... continues until system is complete Requirements evolve with each sprint — they are NOT fixed upfront! ───────────────────────────────────────────────────────── KEY AGILE PRINCIPLE: "Working software over comprehensive documentation" (Requirements documentation is minimized but not eliminated)

User Stories — Agile Requirements Format:

In agile, requirements are written as User Stories on cards or in tools like JIRA:

📐 User Story Format
┌─────────────────────────────────────────────────────────────┐ │ USER STORY FORMAT │ │ │ │ AS A [type of user] │ │ I WANT [some goal/feature] │ │ SO THAT [benefit/reason] │ │ │ │ Example: │ │ "AS A student, │ │ I WANT to see my assignment grades online, │ │ SO THAT I can track my academic progress │ │ without waiting for paper reports." │ │ │ │ Each user story has: │ │ • Acceptance criteria (when is it "done"?) │ │ • Story points (effort estimate) │ │ • Priority (which sprint?) │ └─────────────────────────────────────────────────────────────┘

Key Agile RE Practices:

PracticeDescription
Product BacklogPrioritized list of all user stories. Maintained throughout project. Highest priority items done first.
Sprint PlanningAt start of each sprint, team selects stories from backlog to implement. These become the sprint's requirements.
Product OwnerRepresents the customer. Responsible for the product backlog — prioritizes user stories, clarifies requirements for the team.
Acceptance TestsEach user story has acceptance criteria. Tests written to verify when a story is "done."
Definition of DoneAgreed criteria for when a user story is fully implemented and tested.
Refining BacklogRegularly adding, removing, reprioritizing, and clarifying user stories.

Challenges of Agile RE:

  • Customers must be highly available (Product Owner is a full-time role)
  • Harder to do for large systems with many stakeholders
  • Systems are often outsourced — need a formal contract, not a backlog
  • Regulatory/safety-critical systems may require formal requirements documentation
  • New team members have difficulty understanding the full system when requirements are scattered in stories
🧠 Memory Trick

Agile RE in one sentence: "Gather requirements just-in-time, in small pieces, as user stories, validated by the product owner each sprint."
User Story structure: "As a [WHO] I want [WHAT] so that [WHY]" — Remember: WHO-WHAT-WHY

Final Practice Questions
FINAL Q1

Define Requirements Engineering and explain why it is considered the most critical phase of software development.

Answer

Requirements Engineering (RE) is the systematic process of discovering, analyzing, documenting, and validating the services a system should provide and the constraints under which it must operate.

It is the most critical phase because: (1) Requirements errors caught during RE cost ~1× to fix. The same error found during coding costs ~10×, during testing ~50×, and after deployment ~100× more. (2) ALL subsequent phases (design, coding, testing) are based on requirements — a wrong foundation means everything built on it is also wrong. (3) Most software project failures trace back to incorrect or incomplete requirements, not poor coding.

FINAL Q2

Explain with a diagram the difference between User Requirements and System Requirements. Give an example of each.

Answer
User vs System Requirements
USER REQUIREMENT (high-level, for managers/clients): "The system shall generate monthly financial reports for management." ↓ expands into ↓ SYSTEM REQUIREMENTS (detailed, for developers): 1.1 Report generated on last working day of each month after 17:30 1.2 Report lists each department's expenses with subtotals 1.3 Report exported as PDF and sent to authorized managers by email 1.4 Access restricted to users with Finance-Manager role 1.5 Report generation must complete within 5 minutes

User requirements: high-level, natural language, for non-technical readers. System requirements: detailed, precise, for developers and testers.

FINAL Q3

What is the Requirement Traceability Matrix (RTM)? Why is it important?

Answer

The RTM is a document that maps every requirement to its source (stakeholder), its design component, and its test cases. It provides bidirectional traceability — forward (req → design → tests) and backward (tests → design → req → stakeholder).

Importance: (1) Ensures every requirement is implemented — nothing missed. (2) Enables impact analysis — when a requirement changes, RTM shows all affected components. (3) Proves system meets requirements — can trace every test to a requirement. (4) Required for safety-critical and regulated systems for legal compliance.

FINAL Q4

Explain ethnography as a requirements elicitation technique. What does it discover that interviews miss?

Answer

Ethnography is an observational technique where a requirements analyst immerses themselves in the actual work environment, observing day-to-day work rather than asking questions about it.

What it discovers that interviews miss:

  • Implicit requirements: Things workers do naturally without thinking — so obvious to them they never mention in interviews
  • Actual vs. formal processes: People rarely follow official process diagrams. Ethnography reveals the real workflow
  • Cooperation requirements: How people coordinate with each other, cover for absent colleagues — systems must support this

Best combined with prototyping: ethnography informs the prototype, prototype focuses the next phase of observation.

FINAL Q5

What is requirements validation? How does it differ from requirements verification?

Answer

Requirements Validation: Checking that the requirements define the system the customer ACTUALLY WANTS. "Are we building the RIGHT system?" Done during RE phase.

Requirements Verification: Checking that the system has been built ACCORDING TO the requirements. "Are we building the system RIGHT?" Done during testing phase.

Validation techniques: Requirements reviews, prototyping, test-case generation. Validation is done BEFORE development because fixing requirement errors then is far cheaper than after building the wrong system.

FINAL Q6

What are the advantages of using structured natural language over plain natural language for requirements specification?

Answer
  • Consistency: Standard template ensures all requirements have the same format — easier to read, compare, and audit
  • Completeness: Template fields (inputs, outputs, preconditions, etc.) act as a checklist — harder to miss information
  • Reduced ambiguity: Structure forces requirements to be more precise than free-form text
  • Easier review: Reviewers know exactly where to find each type of information

Limitations: Still not as precise as formal mathematical specifications, so complex computations may still be hard to express clearly (solved by adding tables or diagrams).
