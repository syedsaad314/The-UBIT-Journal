15-Mark Question15 Marks

Q1. Define Requirements Engineering (RE). Explain why poor requirements — rather than poor coding — are cited as the primary cause of software project failures.

  • 1Open with the textbook definition — use the words "discovering, analyzing, documenting, and checking."
  • 2The second half of the question is about WHY — give the cost-multiplication argument (1× → 10× → 100×).
  • 3Reference the Standish Group CHAOS Report for credibility.
  • 4Explain the "foundation" analogy — wrong foundation means everything on top is also wrong.
  • 5End with: RE is not just a phase, it is a risk mitigation strategy.
Definition of Requirements Engineering: Requirements Engineering (RE) is the systematic process of discovering, analyzing, documenting, and checking the services a system should provide and the constraints under which it must operate. It is the very first technical phase of software development and serves as a bridge between what stakeholders need and what developers will build. Why Poor Requirements Cause Project Failure: 1. The Cost Escalation Principle (Boehm's Law) A requirements error caught during RE costs approximately 1x to fix. The same error found: - During design: costs ~3-5x - During coding: costs ~10x - During testing: costs ~50x - After deployment: costs ~100-200x This exponential cost increase means requirements errors are the most economically destructive category of error in software development. 2. Everything Downstream Depends on Requirements Design, architecture, coding, and testing are ALL based on requirements. If the requirements are wrong, the design based on them is wrong. The code based on that design is wrong. The tests that verify against those requirements confirm the wrong thing. The entire system is built on a false foundation. 3. Evidence from Industry (Standish CHAOS Report) The Standish Group's annual CHAOS Report consistently identifies incomplete requirements, lack of user involvement, and unrealistic expectations (all RE failures) as the top causes of software project failure — not inadequate coding skills. 4. The "Wicked Problem" Reality Sommerville notes that large software systems address "wicked problems" — problems that cannot be fully defined upfront. This means RE must be thorough and iterative. Skipping RE means the "wicked problem" remains unsolved and the delivered system solves the wrong problem entirely. 5. Silent but Deadly Errors Requirements errors are particularly dangerous because they are silent — unlike a syntax error that breaks a compile, a wrong requirement produces working software that does the wrong thing. The system passes all tests and fails in production. Conclusion: RE is not just a phase to check off — it is the most critical investment a project can make. Every hour spent in RE can save 10-100 hours of costly rework later.

Classification of Requirements: A) FUNCTIONAL REQUIREMENTS What the system DOES — specific behaviors, services, and functions. Examples (Hospital System): - "The system shall allow staff to search patient records by name or patient ID." - "The system shall generate a daily list of patients for each clinic." - "Staff shall be identified by an 8-digit employee number." Q3. SITUATION: A university's IT team is building a student portal. One requirement says: "The system should be fast, secure, and easy to use." A developer reads this and starts coding. Six months later, the university rejects the system — it logs users out every 30 seconds (too secure), takes 8 seconds to load a page (not fast enough), and requires 14 steps to enroll in a course (not easy). Identify ALL the requirements engineering failures here and how they should have been corrected.

  • 1Identify the scenario type first: this is an NFR specification failure.
  • 2Name each specific failure: ambiguity, no metrics, conflict between requirements.
  • 3Rewrite each requirement correctly — show the examiner you know what a good requirement looks like.
  • 4Mention the "shall vs should" distinction (mandatory vs desirable).
  • 5Connect back to RE process: validation would have caught this before coding.
Requirements Engineering Failures Identified: FAILURE 1 — Vague, Unmeasurable NFRs "Fast, secure, easy to use" are adjectives, not requirements. None of them are verifiable. - "Fast" — fast compared to what? For whom? Under what load? - "Secure" — what threats? What authentication method? Session timeout? - "Easy to use" — measured how? For which user group? FAILURE 2 — No Quantitative Metrics Specified Without metrics, the developer made their own judgment calls: - Security → 30-second timeout (developer's interpretation) - Fast → no performance target specified, so no optimization done - Easy → no usability testing or step-count limit defined FAILURE 3 — Conflicting Requirements Not Resolved "Secure" and "easy to use" are in natural tension. High security (frequent logouts, complex passwords) often reduces usability. This trade-off needed explicit discussion during RE. FAILURE 4 — No Requirements Validation Requirements should have been reviewed with stakeholders BEFORE development began. A simple prototype or walkthrough would have revealed that "30-second logout" is unacceptable. FAILURE 5 — Using "Should" Instead of "Shall" In requirements language, "should" means optional/desirable. "Shall" is mandatory. The requirement used "should" — technically making the entire specification advisory, not contractual. CORRECTED REQUIREMENTS (How they should have been written): ❌ WRONG: "The system should be fast" ✅ RIGHT: "The system SHALL load any page within 2 seconds for up to 500 concurrent users" ❌ WRONG: "The system should be secure" ✅ RIGHT: "The system SHALL automatically log out users after 20 minutes of inactivity. Passwords SHALL be minimum 8 characters with at least one number and one special character." ❌ WRONG: "The system should be easy to use" ✅ RIGHT: "A student SHALL be able to complete course enrollment in a maximum of 5 steps. New students SHALL be able to perform core tasks after 30 minutes of training." Process Fix: After writing corrected requirements, they should have been: 1. Reviewed with university stakeholders for approval 2. Prototyped to verify the session timeout was acceptable 3. Test cases derived from each metric before any coding began

Q1. Describe the Requirements Engineering process as a spiral/iterative model. Explain each stage and justify why RE is iterative rather than linear.

  • 1Draw the spiral: Elicitation → Specification → Validation → back to Elicitation.
  • 2Explain each stage in one solid paragraph each.
  • 3The key insight: each cycle produces more detail and resolves conflicts from the previous cycle.
  • 4Justify iterative nature: requirements change, stakeholders discover new needs, conflicts surface.
  • 5Use the phrase "requirements are not discovered, they are negotiated" — it's memorable and marks-worthy.
The RE Process — Iterative Spiral Model: The RE process is NOT a single pass through a checklist. It is an iterative, spiral process where each cycle deepens understanding and resolves conflicts from the previous cycle. Sommerville represents this as a spiral with three core activities: STAGE 1 — REQUIREMENTS ELICITATION Goal: Discover what stakeholders need. Activities: Interviews, workshops, ethnography, document analysis, prototyping. Output: A draft list of requirements from all stakeholder perspectives. Challenge: Stakeholders may not know what they want; their needs conflict; domain knowledge is tacit. STAGE 2 — REQUIREMENTS SPECIFICATION Goal: Formally write down the discovered requirements. Activities: Write numbered requirements using "shall/should," draw use case diagrams, create structured templates. Output: Draft Software Requirements Specification (SRS). Challenge: Natural language is inherently ambiguous. Mathematical notation is precise but inaccessible to non-technical stakeholders. STAGE 3 — REQUIREMENTS VALIDATION Goal: Check that the requirements define the right system — the one stakeholders ACTUALLY want. Activities: Requirements reviews (inspections), prototyping, test case generation. Output: Validated, approved requirements baseline. Challenge: Validation requires all stakeholders to actively engage — time-consuming. Why Iterative (Not Linear)? The spiral is justified because: 1. Requirements are not discovered — they are negotiated. Each stakeholder has a partial view; the full picture only emerges through repeated discussion. 2. After validation, new issues surface that send the process back to elicitation. 3. Prototypes shown during validation trigger new requirements. 4. Business environment changes during the process — old requirements become outdated. 5. Large systems address "wicked problems" — problems that can only be fully defined as you work on them. Spiral Diagram: Elicitation ↗ ↘ Validation ←── Specification ↘ ↗ Elicitation (next cycle, more detail) Each complete spiral produces a more refined, more complete, more validated set of requirements. Requirements management underpins all three activities throughout.

Q2. Explain the three levels of requirements: Business Requirements, User Requirements, and System Requirements. How do they differ in audience, format, and purpose? Use a single example to trace a requirement across all three levels.

  • 1Use a table to compare all three levels — audience, format, language, detail.
  • 2Trace ONE requirement through all three levels — same idea, different specificity.
  • 3Clarify that Design is NOT a requirement level — a common trick question.
  • 4The hierarchy goes: Business → User → System. Each level expands on the one above.
  • 5Mention the SRS contains both user and system requirements — different sections.
Three Levels of Requirements: LEVEL 1 — BUSINESS REQUIREMENTS What the organization wants to ACHIEVE from the system — goals, not features. Audience: Senior management, investors, project sponsors. Format: Strategic statements, business cases, vision documents. Example: "Reduce appointment booking time by 50% to improve patient throughput." Detail: Very high-level. Says NOTHING about how the software achieves this. LEVEL 2 — USER REQUIREMENTS What USERS need to DO with the system to achieve the business goal. Audience: End users, middle management, clients — non-technical. Format: Natural language, simple diagrams, use cases. Example: "The receptionist shall be able to book an appointment in 3 steps or fewer, with automatic slot suggestions based on doctor availability." Detail: Describes user tasks — still solution-independent. LEVEL 3 — SYSTEM REQUIREMENTS The detailed technical behavior the system must exhibit to satisfy user requirements. Audience: Developers, architects, testers. Format: Numbered requirements with shall/should, UML diagrams, data models. Examples: - "3.1 The system shall retrieve available appointment slots within 1 second of entering the patient's GP code." - "3.2 Slots shall be displayed in ascending chronological order." - "3.3 Confirmed bookings shall trigger an SMS to the patient within 30 seconds." Detail: Precisely testable, technically specific. Comparison Table: Level | Audience | Language | Detail Business | Management/Sponsors| Strategic | Lowest — goals only User | Clients/End Users | Natural language | Medium — tasks and scenarios System | Developers/Testers | Technical/Precise | Highest — implementable ⚠️ Common Trick: "Design" is NOT a requirements level. Design answers HOW the system will be built — architecture, algorithms, database schema. Requirements describe WHAT the system must do. A requirement that specifies a particular technology ("use MySQL") has crossed into design territory and violates the solution-independence principle. The Hierarchy in Practice: Business Req → broken down into → User Reqs → expanded into → System Reqs → implemented as → Code → tested against → System Reqs → validated against → User Reqs → verified against → Business Reqs

Q3. SITUATION: A startup's CEO says: "We need a mobile app that makes it easier for people to find parking in Karachi." The project manager writes this verbatim as the only requirement and hands it to the development team. Three months later, the app is built but the CEO rejects it saying "This isn't what I meant at all." Using the three levels of requirements, explain what went wrong and how the requirement should have been properly developed.

  • 1Identify the problem: the CEO's statement is a Business Requirement, not a full specification.
  • 2Explain what was missing: user requirements and system requirements were never derived.
  • 3Write what the proper User Requirements would look like for this scenario.
  • 4Then give sample System Requirements derived from them.
  • 5Conclude: skipping the hierarchy creates an interpretation vacuum that developers fill with guesswork.
What Went Wrong — Analysis: The CEO's statement ("easier to find parking") is a Business Requirement — it expresses a HIGH-LEVEL GOAL only. The project manager made a fatal error: he skipped the elicitation process and handed this to developers as if it were a complete specification. This left the developer with zero guidance on: - WHO the users are (drivers? parking lot owners? both?) - WHAT actions users need to perform - HOW "easier" is measured - What makes current parking finding "hard" in Karachi's specific context The development team filled this interpretation vacuum with their own assumptions — and those assumptions did not match the CEO's mental model. Proper Requirements Development: BUSINESS REQUIREMENT (what was given): "Enable drivers in Karachi to find available parking spots faster, increasing app daily active users to 10,000 within 6 months." USER REQUIREMENTS (what should have been elicited via interviews/workshops with drivers and parking lot owners): - "As a driver, I shall be able to see all available parking spots within 500m of my current location on a map." - "As a driver, I shall be able to reserve a spot 30 minutes in advance." - "As a parking lot owner, I shall be able to update real-time availability of my spaces." - "A driver shall receive navigation directions to their reserved spot." SYSTEM REQUIREMENTS (derived from user requirements): - "The system shall detect the user's GPS location and display all parking facilities within a 500m radius within 3 seconds." - "Parking spot availability shall refresh every 60 seconds via the parking owner's app or sensor API." - "Reservations shall be held for 15 minutes before automatic release." - "The system shall integrate with Google Maps API for turn-by-turn navigation." Root Cause of Failure: By missing the user requirements elicitation stage, the team had NO information about Karachi-specific challenges (cash-only parking, no GPS sensors, informal lots). The app they built assumed sensor-equipped lots — which do not exist in Karachi. The requirements hierarchy exists precisely to prevent this mismatch.

Q1. Explain the Requirement Traceability Matrix (RTM). What is forward and backward traceability? Why is it especially critical for safety-critical systems?

  • 1Define RTM first — it maps Req# → Source → Design → Test Case.
  • 2Draw the RTM table structure — always earns marks.
  • 3Forward = req to code; Backward = test to stakeholder. Use arrows in explanation.
  • 4For safety-critical: regulatory bodies REQUIRE traceability as legal evidence of compliance.
  • 5Give an example domain: aviation, medical devices, nuclear — any one works.
Requirement Traceability Matrix (RTM): The RTM is a document (usually a table or tool) that maps every requirement to its origin, its implementation in design and code, and the test cases that verify it. It provides a complete audit trail for every requirement throughout the software lifecycle. RTM Structure: ┌──────┬──────────────────┬──────────────┬────────────┬────────────────┐ │ REQ# │ DESCRIPTION │ SOURCE │ DESIGN │ TEST CASE │ ├──────┼──────────────────┼──────────────┼────────────┼────────────────┤ │ R001 │ User login │ Sec. Manager │ Module-A │ TC-001, TC-002 │ │ R002 │ Search records │ Doctor │ Module-B │ TC-003 │ │ R003 │ Generate report │ Manager │ Module-C │ TC-004, TC-005 │ │ R004 │ Data encryption │ IT/Legal │ Module-D │ TC-006 │ └──────┴──────────────────┴──────────────┴────────────┴────────────────┘ FORWARD TRACEABILITY: Direction: Requirement → Design Component → Code → Test Case Purpose: Ensures every requirement is implemented. "Has R002 been designed, coded, and tested?" Use: During development — tracks progress and ensures nothing is missed. BACKWARD TRACEABILITY: Direction: Test Case → Code → Design → Requirement → Stakeholder Purpose: Explains WHY something exists. "Why does TC-003 exist? Because of R002. Why does R002 exist? Because the Doctor (stakeholder) needs it." Use: Impact analysis — when something changes, trace backward to find the stakeholder and forward to find all affected code. Why Critical for Safety-Critical Systems: 1. Regulatory Compliance: Aviation (DO-178), medical devices (FDA 21 CFR), nuclear, and defense standards legally require that every requirement be traceable to a test case. Without RTM, the regulator will reject the system. 2. Impact Analysis: If a flight-control algorithm requirement changes, the RTM immediately shows which design components, code modules, and test cases are affected. In safety-critical systems, missing one affected component could be catastrophic. 3. Verification Evidence: The RTM proves to regulators that the system was built to its requirements — not assumptions. It is legal evidence. 4. No Orphan Requirements: Every requirement must have at least one test case. An untested requirement in a safety-critical system is an unverified claim about safety. Example: In a pacemaker software system, requirement R047 states "Device shall detect ventricular fibrillation within 3 seconds." The RTM links this to the arrhythmia detection module and test case TC-047 that verifies detection speed. If the detection algorithm is later changed, the RTM immediately flags TC-047 as affected — preventing a safety-critical oversight.

Q2. Classify and explain the four types of volatile requirements: Mutable, Emergent, Consequential, and Compatibility requirements. Provide a realistic example for each.

  • 1First distinguish enduring vs. volatile requirements as the parent concept.
  • 2For each volatile type: name it, define it, give one concrete example.
  • 3Mutable = business/environment changes; Emergent = new when system is seen; Consequential = caused by new system; Compatibility = old system integration.
  • 4Explain WHY identifying volatility matters: these reqs need extra management attention.
  • 5A table summarizing all four at the end is a strong closing technique.
Enduring vs. Volatile Requirements: ENDURING REQUIREMENTS: Stable requirements tied to the core purpose of the organization. They rarely change. Example: "The system shall maintain patient medical records." This is fundamental — it won't change while the hospital exists. VOLATILE REQUIREMENTS: Requirements likely to change during development or after deployment. Sommerville classifies four types: 1. MUTABLE REQUIREMENTS Definition: Requirements that change because of changes in the business environment, political environment, or technology. Example: A tax calculation module has the requirement "VAT rate shall be 17% for all taxable goods." When the government changes VAT to 18%, this requirement must change — not due to any software issue, but due to external law. Management: Flag these early. Monitor external factors (laws, regulations, market) that could trigger changes. 2. EMERGENT REQUIREMENTS Definition: Requirements that only emerge (surface) after the customer has seen and used the system or a prototype — they could not have been anticipated upfront. Example: A social media platform builds a "post" feature. After seeing it, users say "We also need an edit button" and "We need character count visible while typing." These requirements emerged only when users interacted with the real system. Management: Plan for iterations. Build prototypes early to surface emergent requirements cheaply. 3. CONSEQUENTIAL REQUIREMENTS Definition: Requirements that arise as a consequence of introducing the new system — the new system creates new needs that didn't exist before. Example: A hospital introduces electronic prescription software. This CREATES the new requirement: "All electronic prescriptions must be backed up every 15 minutes to prevent data loss." Paper prescriptions never needed this. The new system caused this new requirement. Management: Think through second-order effects of the new system during requirements planning. 4. COMPATIBILITY REQUIREMENTS Definition: Requirements that arise because of the need to interface with existing systems, legacy software, or hardware that cannot be changed. Example: A new HR system must interface with a 25-year-old payroll system that only outputs CSV files in a specific format. The new system gains the requirement: "Must import employee data from CSV files with columns in the format: EmpID, Name, Department, Salary." This requirement exists only because of the old system. Management: Conduct thorough interface analysis with all legacy systems early in the project. Summary Table: Type | Trigger Source | Example Trigger Mutable | Business/external change | New government regulation Emergent | User sees working system | Prototype feedback session Consequential | New system creates needs | Need for backups after going digital Compatibility | Legacy system constraint | Old payroll CSV format

Q3. SITUATION: A government built a land registration system in 2010. In 2024, the government changed property tax laws, new biometric ID cards were introduced, and users complained that online features they never asked for in 2010 (e-payment, SMS alerts) are now essential. Additionally, the new system must integrate with the 2010 database. Classify each of these changes using the volatile requirement types and explain how each should be managed.

  • 5Conclusion: volatile requirement classification is not academic — it drives the management response.
Classification and Management: CHANGE 1: New property tax laws (2024) Type: MUTABLE REQUIREMENT Reason: The business/legal environment changed externally. The software requirement "tax rate = X%" must be updated to reflect new law. No amount of planning in 2010 could have predicted the 2024 tax structure. Management: The RE team should have flagged tax calculation as a volatile requirement in 2010. A formal change request should now be raised → impact analysis using RTM → update SRS → re-test all tax-related modules. CHANGE 2: E-payment and SMS alerts now considered essential Type: EMERGENT REQUIREMENT Reason: In 2010, these features didn't exist in the users' mental model. After 14 years of using online banking and mobile apps, users' expectations have changed. These requirements only emerged because users experienced digital services and now expect them everywhere. Management: This is where iterative requirements review is essential. Annual or biennial re-elicitation sessions would have surfaced these emerging needs before they became urgent pain points. Now, a new elicitation cycle must be run to specify these properly. CHANGE 3: New biometric national ID cards introduced Type: CONSEQUENTIAL REQUIREMENT Reason: The government's decision to issue biometric IDs creates a NEW requirement for the land system: "The system shall verify property owner identity using the NADRA biometric API." Management: Perform a "consequential requirement scan" — systematically ask "What new requirements does this new technology/policy create?" The biometric integration must be fully specified as a new set of requirements. CHANGE 4: New system must use 2010 database Type: COMPATIBILITY REQUIREMENT Reason: The legacy database has a fixed schema, data formats, and access methods. The new system must work with it. These are not user needs — they are technical constraints imposed by the existing infrastructure. Management: Conduct thorough interface analysis of the 2010 database: its schema, data types, access methods, performance characteristics. Write compatibility requirements specifying exactly how the new system reads from and writes to the old database. Overall Management Recommendation: - Use RTM to track all four new requirement sets - Create separate section in updated SRS for each volatile requirement type - Flag tax calculation and external ID integration as HIGH VOLATILITY for ongoing monitoring - Establish a formal Requirements Change Board to process all future changes through controlled process

Q1. Explain the MoSCoW prioritization method in detail. Compare it with the Kano Model and the 100-Dollar Test. When would you choose each?

  • 1MoSCoW: spell out all four letters with meaning and example for each category.
  • 2Kano: explain the three satisfaction types — Basic (must), Performance (more = better), Excitement (delight).
  • 3100-Dollar Test: stakeholders spend 100 points — forces honest prioritization.
  • 4Use a comparison table — audience, best use case, limitation.
  • 5"When to choose" answers are often what professors test — don't skip this.
MoSCoW Prioritization Method: MoSCoW is the most widely used requirement prioritization technique. Each letter represents a priority category: M — MUST HAVE (Non-negotiable) The system CANNOT function without these. If any Must Have is missing, the release fails. Example: "User authentication" in a banking app — without it, the app cannot be used. S — SHOULD HAVE (Important but not critical) High-value requirements that are not strictly essential for launch but are expected. Example: "Export transaction history as PDF" — important, but the bank can operate without it. C — COULD HAVE (Nice to have) Low-priority requirements that add value but have no significant impact if omitted. Example: "Dark mode" — users would appreciate it but won't stop using the app without it. W — WON'T HAVE (Explicitly deferred) Requirements acknowledged but consciously excluded from this release. Documented to manage expectations. Example: "Multi-currency support" — planned for v2.0, explicitly not in v1.0. Value of MoSCoW: Prevents scope creep by forcing explicit decisions. "Won't Have" is especially powerful — it lets stakeholders know a feature is coming, just not now. --- Kano Model: The Kano Model prioritizes by the relationship between feature presence and user satisfaction: 1. Basic (Must-Be) Features: Expected by users but do not create satisfaction when present — only dissatisfaction when absent. Example: A car's brakes — nobody is delighted that brakes work, but everyone is furious if they don't. 2. Performance Features: More = better. Satisfaction is directly proportional to how well these work. Example: Laptop battery life — the longer, the happier the user. 3. Excitement (Delighter) Features: Unexpected features that create strong positive satisfaction. Users don't know they want them, but love them when they get them. Example: A car that automatically parks itself. Best for: Customer-focused product development where understanding user emotions and delight matters. --- 100-Dollar Test (Cumulative Voting): Stakeholders are given 100 "dollars" (points) to distribute across requirements. They spend more on requirements they value most. Process: 1. List all requirements 2. Each stakeholder distributes 100 points across requirements 3. Total points per requirement across all stakeholders determines priority Advantage: Forces stakeholders to make real trade-offs. If they put 80 points on one requirement, they have only 20 left for everything else — it reveals true priorities, not wishful thinking. Best for: Stakeholder workshops where political dynamics might otherwise distort priorities. Comparison Table: Method | Best For | Limitation MoSCoW | Clear, fast prioritization | Binary — no gradation within categories Kano | Understanding user satisfaction | Requires market/user research 100-Dollar | Group workshops, revealing priorities | Time-consuming with many requirements Choose MoSCoW when: You need a quick, stakeholder-readable classification for sprint planning. Choose Kano when: You are building a user-facing product and need to understand emotional impact. Choose 100-Dollar when: Multiple competing stakeholders need to negotiate priorities democratically.

Q2. What is trade-off analysis in requirements engineering? Using the project triangle, explain how conflicting requirements (security vs. performance, features vs. time-to-market) must be resolved.

  • 1Define trade-off analysis as the evaluation of competing constraints to find optimal balance.
  • 2Draw the project triangle: Time, Cost, Scope — pick any two.
  • 3Give at least two real trade-off pairs: security vs. performance, features vs. deadline.
  • 4Explain the process: identify, quantify, discuss with stakeholders, document the decision.
  • 5The key message: trade-offs are not failures — they are deliberate, documented decisions.
Trade-off Analysis in Requirements Engineering: Trade-off analysis is the systematic process of evaluating competing requirements or constraints to identify the best achievable balance given the project's resources and priorities. In RE, trade-offs must be made explicit, documented, and decided by stakeholders — not silently resolved by developers. The Project Triangle: SCOPE/QUALITY △ /│\ / │ \ / │ \ /Pick any\ / 2 \ /────────────\ TIME COST Rule: Optimizing all three simultaneously is impossible. Improving scope requires either more time, more cost, or both. This constraint forces deliberate trade-off decisions. Common Trade-off Scenarios in RE: TRADE-OFF 1: Security vs. Performance - More security (encryption, authentication checks, session management) = slower response times and more processing overhead. - Example: A banking app requires 256-bit AES encryption, multi-factor authentication, and 2-minute session timeout. Each of these adds latency and processing load. - Resolution: Benchmark the performance impact of each security measure. Accept the performance cost if security is a MUST HAVE. Consider hardware upgrades (cost trade-off) to achieve both. TRADE-OFF 2: Features vs. Time-to-Market - More features = longer development time and missed launch window. - Example: A startup has 40 requirements but only 3 months. Implementing all 40 means a 9-month timeline — and the competitor launches in 3. - Resolution: Apply MoSCoW. Launch with 10 Must Haves in 3 months. Schedule Should Haves for v1.1 in month 6. The trade-off is explicitly: reduced scope in exchange for competitive timing. TRADE-OFF 3: Usability vs. Security - Highly secure systems often require complex passwords, frequent re-authentication, and multi-step processes — all of which reduce usability. - Resolution: Define minimum acceptable thresholds for both (e.g., "max 2 steps to login" AND "must use MFA"). Test both requirements in combination. Quantify the impact of each option (how much slower? how much more expensive?) 3. Present options to stakeholders with trade-off consequences 4. Q2. What is Requirements Management? Explain its key activities and explain why requirements management is necessary even after the SRS has been baselined and signed off.

  • 2Key activities: change control, traceability, status tracking, version control.

Requirements Management: Requirements Management is the systematic process of tracking, controlling, and maintaining requirements throughout the entire software development lifecycle — from initial elicitation through delivery and beyond. It is an ONGOING activity, not a phase that ends when the SRS is signed. Key Activities of Requirements Management: 1. REQUIREMENTS IDENTIFICATION AND TRACKING Assign every requirement a unique identifier (e.g., FR-001, NFR-012). This enables every requirement to be tracked through the lifecycle. CHANGE CONTROL Establish a formal process for handling requirement changes: - Change request submission - Impact analysis - Approval/rejection by Change Review Board - Implementation and SRS update - Stakeholder notification Without change control, requirements creep in informally, scope expands without adjustment to budget/time, and the project fails. 3. TRACEABILITY MAINTENANCE Keep the RTM current as requirements are added, changed, or removed. Ensure every requirement always links to its design component and test case. Without maintained traceability, impact analysis becomes guesswork. 4. STATUS TRACKING Track the status of every requirement through its lifecycle: Proposed → Approved → Implemented → Verified → Delivered This provides real-time visibility into project progress. 5. Business Environment Changes: New laws, market shifts, competitor actions force requirement updates. 2. Stakeholder Understanding Evolves: After signing, stakeholders see prototypes and realize their requirements were wrong. They need a controlled way to make corrections. 3. Technical Discovery: Architects discover during design that a requirement is technically infeasible. It must be renegotiated. 4. Emergent Requirements: Usage of prototypes surfaces requirements that were simply unknown at baseline time. 5. Scope Creep Threat: Without active management, informal additions accumulate. Management provides the disciplined channel for all changes. Real-World Tools: IBM DOORS, Jira (with requirements plugins), ReqIF format, Confluence — these tools automate traceability, change tracking, and status reporting at scale. In Summary: An SRS baseline is a starting point, not an endpoint. Requirements management is the discipline that keeps the baseline aligned with reality throughout the project's life.

Q1. Explain the relationship between requirements and software architecture. Why should requirements and architecture be developed in parallel rather than sequentially?

  • 1Key idea: NFRs especially drive architecture — they constrain design choices fundamentally.
  • 2The "impossible NFR" problem: some NFRs make certain architectures technically infeasible.
  • 3Parallel development prevents "impossible architecture" surprises late in the project.
  • 4Use the famous story structure: NFR states "10,000 TPS" → architect says "that's impossible with that design."
  • 5Mention the concept of "architecturally significant requirements" — only a subset of reqs drive architecture.
Relationship Between Requirements and Architecture: Requirements and architecture have a bidirectional, deeply interdependent relationship: - Requirements DRIVE architecture: they determine what the system must do and how well it must do it. - Architecture CONSTRAINS requirements: what is technically feasible limits what can be promised. Neither can be completely defined without the other. This makes sequential "complete requirements, then design architecture" a flawed approach. Architecturally Significant Requirements (ASRs): Not all requirements affect architecture equally. ASRs are a subset of requirements that have the greatest influence on architectural decisions. Typically these are: - Performance NFRs ("100,000 concurrent users") - Reliability NFRs ("99.99% uptime") - Security NFRs ("end-to-end encryption") - Critical functional requirements ("real-time processing") How NFRs Drive Architecture — Examples: NFR: "System shall handle 10,000 transactions per second" → This eliminates single-server monolithic architecture. → Forces distributed architecture, message queues (Kafka), in-memory databases (Redis), horizontal scaling. NFR: "System shall be available 99.999% of the time (5.26 minutes downtime/year)" → Requires redundant servers in multiple geographic locations, automatic failover, load balancers. NFR: "All patient data shall be encrypted in transit and at rest" → Requires TLS throughout, encrypted database columns, key management infrastructure. Why Parallel Development (Not Sequential): Sequential Problem (Requirements First, Then Architecture): Stage 1: Complete all 200 requirements → SRS signed off Stage 2: Architect studies SRS and discovers: Requirement R-047 ("respond in 0.5 seconds globally") is physically impossible with any current architecture. The speed of light limits cross-continental round-trips to ~80ms, and that is before any processing. Result: The SRS must be re-opened, R-047 renegotiated, stakeholders re-consulted. Months of work wasted. Parallel Development Solution: As requirements are being elicited and specified, a parallel "architecture spike" evaluates feasibility. When R-047 is first proposed, the architect immediately flags it as potentially infeasible. The requirement is refined IN REAL TIME: "respond in 0.5 seconds from within Pakistan, 2 seconds internationally." The SRS is correct from the start. Architecture also reveals MISSING requirements: When the architect designs the distributed system, they realize: "We need a requirement for database consistency under network partition — nobody specified this." This discovers a completeness gap. Bidirectional Feedback Loop: Requirements Team ←→ Architecture Team "Can we have X?" ←→ "X requires Y cost/complexity — is that acceptable?" "What's feasible?" ←→ "Z is feasible; A is not" "We're adding W" ←→ "W requires redesigning module B" This continuous dialogue during elicitation prevents architectural surprises and ensures the requirements baseline is technically realistic.

Q1. Explain Requirements Validation. What are the five checks performed during validation, and how does validation differ from verification?

  • 1The validation vs. verification distinction is a CLASSIC tricky question — nail it first.
  • 2Validation = "Are we building the right system?" Verification = "Are we building the system right?"
  • 3Five checks: Validity, Consistency, Completeness, Realism, Verifiability.
  • 4Validation techniques: requirements reviews, prototyping, test case generation.
  • 5Cost argument: finding errors in validation costs far less than finding them after coding begins.
Requirements Validation vs. Verification: These two terms are frequently confused — they answer fundamentally different questions: VALIDATION: "Are we building the RIGHT system?" - Checks that the requirements represent what stakeholders actually need - Done DURING and AFTER the RE phase, BEFORE development begins - Example: Does this SRS describe the hospital system the doctors and nurses actually need? VERIFICATION: "Are we building the system RIGHT?" - Checks that the built system conforms to its specification - Done DURING and AFTER development, comparing the built system against the SRS - Example: Does the built hospital system implement everything in the SRS correctly? Simple memory device: Validation = Right product | Verification = Built correctly The Five Validation Checks (Sommerville): 1. VALIDITY CHECK "Does each requirement actually reflect what the user needs?" Even if a user stated a requirement, it may not be what they truly need. Example: A user says "Add a print button to every screen." True need: access information quickly. The solution (print button) may not be the best one. Validity checks surface this mismatch. 2. CONSISTENCY CHECK "Do any requirements contradict each other?" Example: R-001 says "Session expires after 5 minutes for security." R-015 says "Users should be able to complete complex 20-field forms without re-logging in." These contradict — a consistency check catches this before code is written. 3. COMPLETENESS CHECK "Are all functions, constraints, and constraints that the user needs included?" Are there scenarios where the system would receive input but have no defined behavior? Are all user types' needs represented? Completeness is checked by systematically tracing: for every stakeholder, for every task they perform, is there a corresponding requirement? 4. REALISM CHECK "Can each requirement be implemented within available budget, schedule, and technology?" Example: "Facial recognition response within 0.1 seconds on 1990s hardware." Unrealistic. The realism check involves the architect reviewing requirements for technical feasibility. Unrealistic requirements must be negotiated down to achievable levels. 5. VERIFIABILITY CHECK "Can a test case be written to definitively prove this requirement is met?" Example: "System shall be user-friendly." UNVERIFIABLE. Cannot write a test case for "user-friendly." "System shall allow user to complete login in fewer than 3 taps." VERIFIABLE. Test: count the taps. Every requirement that cannot be verified must be rewritten or removed. Validation Techniques: A) REQUIREMENTS REVIEWS (Inspections) A team of stakeholders and engineers systematically reads through the SRS, checking each requirement against the five checks above. Errors found are documented and assigned for correction. B) PROTOTYPING An executable prototype (mock-up) is built and shown to stakeholders. Seeing the system in action surfaces requirements errors that paper-based review misses. Most powerful for discovering invalid and incomplete requirements. C) TEST CASE GENERATION Attempting to write test cases for each requirement simultaneously validates the requirement. If you cannot write a test case, the requirement fails the verifiability check. Cost Justification: Studies show that a requirements error found during validation costs 1-5× to fix. The same error found during testing costs 50×. The same error found after deployment costs 100-200×. Validation is the highest-ROI activity in RE.

PROBLEM 4: AMBIGUOUS REQUIREMENTS PASSING REVIEW Description: Vague, unmeasurable requirements ("fast," "secure," "user-friendly") pass the review process and enter the SRS. Consequence: Developers implement their own interpretation. Different team members implement the same requirement differently. Testing is impossible. Stakeholder rejection at delivery. Solution: Mandatory verifiability check for every requirement. Automated requirement quality checkers that flag words like "fast," "good," "easy," "modern." Every NFR must have a measurable metric. PROBLEM 5: SCOPE CREEP WITHOUT CHANGE CONTROL Description: New requirements are added informally (verbally, by email) without going through the change management process. Consequence: Scope expands without budget or timeline adjustment. Delivery is delayed. Budget overruns. Stakeholders blame the team for "not delivering on time" not realizing they added 30% more scope mid-project. Solution: Formal change control process. No verbal approvals. CR form required for all changes. Change Review Board approval for anything affecting scope, budget, or timeline. PROBLEM 6: UNCLEAR OWNERSHIP OF REQUIREMENTS Description: No named stakeholder "owns" each requirement. Nobody is accountable when a requirement needs clarification or changes. Consequence: Requirements go unresolved during development. Developers make assumptions. Conflicts between requirements have no owner to resolve them. Changes have no approver. Solution: Every requirement must have a named Owner (a specific stakeholder who requested it and can approve changes to it). Owner is recorded in the SRS and RTM. PROBLEM 7: REQUIREMENTS DOCUMENTATION NOT MAINTAINED AFTER BASELINE Description: The SRS is written once, baselined, and then never updated as changes are made. Consequence: By midway through development, the actual system requirements exist only in developers' heads — not in any document. New team members have no accurate source of truth. Maintenance engineers inherit an outdated SRS. Solution: Mandatory SRS update as part of every approved change. Version-controlled SRS. Change log maintained in the Preface section recording every change and rationale. Legal and RE Analysis: LEGAL POSITION: In contract law, "obviously implied" is generally NOT a valid legal basis for scope inclusion. The SRS is a legal document. HOWEVER: Both parties share RE failures that caused this dispute. NAVY'S RE FAILURE: The Navy failed to conduct thorough domain requirement elicitation. Satellite communication tracking is a fundamental capability for any serious naval fleet management system. This is a DOMAIN REQUIREMENT — one so obvious in the military maritime domain that the Navy assumed it was "obviously implied." This is the classic implicit/tacit knowledge problem. Domain experts do not state what they consider obvious. Additionally, the Navy did not adequately review the SRS before signing. 300 pages is extensive, but a requirement this significant should have been noticed as absent during the review period. SOFTWARE COMPANY'S RE FAILURE: A professional RE team developing a naval fleet management system should have: 1. Conducted domain analysis of naval fleet management to understand what capabilities such systems MUST have 2. Employed a maritime domain expert as consultant during elicitation 3. Explicitly listed scope EXCLUSIONS: "This system will NOT include: [list]." The absence of satellite tracking from the exclusion list OR the inclusion list is a specification failure. 4. Asked during clarification: "A fleet management system typically includes X, Y, Z. Please confirm whether these are in scope." The company should have identified the missing capability through domain expertise and raised it during requirements review — not waited to be told. Root Cause: The fundamental problem is that "fleet management system" is an ambiguous phrase that means different things to different people. The SRS should have defined the scope with explicit capability lists, not relied on the phrase. SCOPE DEFINITION SECTION in SRS: "This system SHALL include the following capabilities: [exhaustive list]. The following capabilities are explicitly EXCLUDED from this contract: [list]. DOMAIN EXPERT REVIEW: The company should have engaged a retired naval officer or maritime systems engineer to review the SRS for domain completeness. 3. REQUIREMENTS WORKSHOP WITH NAVAL OPERATIONS STAFF: Not just procurement officers. The actual fleet commanders should have reviewed the requirements. 4. GLOSSARY DEFINITION: "Fleet Management System" should have been defined in the SRS glossary with a specific capability scope. Resolution Proposal: Neither party should pursue legal action — it is expensive and damages the relationship. Agile Requirements Engineering: In agile methodologies (Scrum, XP, Kanban), requirements are NOT fully specified upfront in a comprehensive SRS. Instead, requirements emerge and evolve through iterative cycles (sprints), with constant customer involvement and feedback. Core Philosophy: "Welcome changing requirements, even late in development." (Agile Manifesto) USER STORIES — The Agile Requirement Format: Format: "As a [user role], I want to [capability/feature], so that [benefit/reason]." This three-part format ensures every requirement captures: - WHO needs it (user role) - WHAT they need (capability) - WHY they need it (benefit — the most important and most often omitted part) Examples: "As a bank customer, I want to transfer money using a mobile number, so that I don't need to know the recipient's full account number." "As a hospital administrator, I want to see daily patient admission statistics on a dashboard, so that I can allocate staff efficiently." "As a student, I want to receive email reminders 24 hours before assignment deadlines, so that I never miss a submission." ACCEPTANCE CRITERIA — The Agile Verifiability Check: Every user story must have acceptance criteria: specific, testable conditions that define when the story is "done." Example Acceptance Criteria for the bank transfer story: ✅ Transfer completes within 5 seconds ✅ Confirmation SMS sent to both sender and receiver within 30 seconds ✅ Transaction visible in statement immediately after completion ✅ If mobile number not registered, error message displayed: "Recipient not registered for mobile transfers" ✅ Transfer fails gracefully if network is unavailable, with no money deducted PRODUCT BACKLOG: The product backlog is the ordered list of all user stories for the system. The Product Owner (a stakeholder representative) maintains and prioritizes the backlog. Items at the top are most important and most detailed; items at the bottom are vague and will be refined when they move up. CONTRACTED/ACQUISITION SYSTEMS: A legal contract requires a complete specification upfront. "We'll figure it out in sprints" is not acceptable in a contract. 2. The Product Backlog: The product backlog is the single authoritative source of all work the team might do. It is an ORDERED list (not just a list — ordered by priority, value, and urgency) of user stories, features, bug fixes, and technical work. The Product Owner is responsible for its content and ordering. Backlog Properties: - Visible and transparent to everyone - Single source of truth for all requirements - Continuously evolving — never "done" - Items at top: small, detailed, ready to implement - Items at bottom: large, vague, will be refined when they approach the top BACKLOG GROOMING (REFINEMENT): Backlog grooming is a regular meeting (typically once per sprint) where the team and Product Owner: 1. ESTIMATE effort (using story points, T-shirt sizing, or planning poker) 5. REPRIORITIZE based on new information, changing business needs Example of Story Splitting: Epic (too large): "As a user, I want to manage my profile" Split into: - "As a user, I want to update my profile photo" - "As a user, I want to change my email address with verification" - "As a user, I want to change my password with current password confirmation" - "As a user, I want to deactivate my account" SPRINT PLANNING: At the start of each sprint (1-4 weeks), the team holds a sprint planning session: 1. Based on team CAPACITY (velocity), select stories that fit in the sprint 5. PRIORITIZE stories based on business value, risk, and dependencies 3. WRITE or APPROVE acceptance criteria for each story 4. CLARIFY requirements when developers have questions (available daily) 5. ATTEND sprint reviews and accept/reject completed stories 6.   • CEach cycle of elicitation, specification, and validation produces more detailed and refined requirements
  • DThe process must restart from scratch when requirements change
✅ C. The spiral means iterative deepening — each pass through the three activities produces more detail and resolves issues from the previous pass. D is wrong: the spiral does NOT restart from scratch; it builds progressively on previous cycles.
Q07 · Topic: SRS / Specification Formats

In SRS documentation, which notation offers the HIGHEST precision but LOWEST accessibility to non-technical stakeholders?

  • ANatural language
  • BUse case diagrams
  • CStructured natural language
  • DMathematical/formal specification (e.g., Z notation)
✅ D. Mathematical/formal notation (Z, state machines) is maximally precise and machine-verifiable, but requires specialist mathematical training to read/write. Used for safety-critical systems (medical, aviation, nuclear). Natural language is the opposite: maximum accessibility, minimum precision.
Q08 · Topic: MoSCoW

In MoSCoW, the "Won't Have" category means:

  • AThe feature is permanently rejected and will never be built
  • BThe feature is explicitly excluded from THIS release but may be included in future releases
  • CThe feature is optional and can be added if time permits
  • DThe feature is technically impossible to implement
✅ B. This is one of the most commonly misunderstood aspects of MoSCoW. "Won't Have" is not permanent rejection — it's a deliberate deferral to a future release. It's actually a POSITIVE tool because it acknowledges the request, manages expectations, and provides a roadmap path. C describes "Could Have."
Q09 · Topic: Agile RE

The correct format for a user story is:

  • A"The system shall allow users to perform [action]"
  • B"As a [role], I want to [capability], so that [benefit]"
  • C"When [event] occurs, the system shall [response]"
  • D"Function [name]: Input [x], Output [y], Action [z]"
✅ B. The canonical user story format. A is traditional "shall" specification. C is an event-driven specification. D is structured natural language template. Only B captures the who + what + why — the essential three-part structure of a user story.
Q10 · Topic: RE Validation

"The system shall be user-friendly" fails which validation check?

  • AValidity check
  • BConsistency check
  • CCompleteness check
  • DVerifiability check
✅ D. Verifiability — no test case can definitively prove or disprove "user-friendly." It's unmeasurable as stated. Tricky: students sometimes say Validity (A). Validity checks whether the requirement reflects what the user truly needs — "user-friendly" might be valid as a goal but it fails as a written requirement because it cannot be verified.
Q11 · Topic: Stakeholders

Which of the following is NOT typically considered a stakeholder in software requirements?

  • AThe system purchaser (client)
  • BExternal regulatory bodies
  • CThe hardware manufacturer of the server the software will run on
  • DEnd users who interact with the system daily
✅ C. A hardware manufacturer is not a stakeholder in the software requirements process — they don't have requirements FOR the system, they impose CONSTRAINTS (hardware specifications the software must work within). All other options have genuine requirements or authority over requirements. Tricky because hardware constraints DO influence requirements — but the manufacturer is a constraint source, not a stakeholder.
Q12 · Topic: Requirements Levels

A document containing high-level statements of system services written in natural language, intended for non-technical customers, represents:

  • ASystem requirements
  • BUser requirements
  • CDesign requirements
  • DBusiness requirements
✅ B. User requirements: natural language, services description, non-technical audience. System requirements (A) are detailed and technical, for developers. Business requirements (D) are even higher-level strategic goals. Design requirements (C) don't exist as a standard level in Sommerville's framework — this is a distractor. Watch for it in exams.
Q13 · Topic: Gold-Plating

A developer adds AI-powered search to the system even though the requirement only specified basic keyword search, believing "users will love it." This is called:

  • ARequirements creep
  • BGold-plating
  • CScope management
  • DFeature elicitation
✅ B. Gold-plating is developer-side scope addition — adding features beyond what was specified. Requirements creep (A) comes from CLIENT/STAKEHOLDER side — they add features. The distinction: who is adding the extra feature? Client → creep. Developer → gold-plating.
Q14 · Topic: Traceability

Using the RTM to find which code modules, design components, and test cases will be affected by a proposed change is called:

  • AForward traceability
  • BBackward traceability
  • CImpact analysis
  • DRisk analysis
✅ C. Impact analysis uses the RTM to determine what will be affected by a proposed change. Tricky: Forward traceability (A) is the direction REQ→DESIGN→CODE (a property of the RTM). Backward traceability (B) is CODE→REQ direction. Impact analysis is the ACTIVITY that uses both directions to assess a change's scope.
Q15 · Topic: Acquisition vs Product Org

In which organizational context does the SRS function as a legally binding contract?

  • AProduct organization (building for general market)
  • BBespoke development (small team, direct client)
  • CAcquisition organization (buyer contracts external supplier)
  • DSupplier organization (multiple named clients)
✅ C. Acquisition organization — government/large corp buys from external supplier via formal contract. The SRS IS the contract. Any ambiguity becomes a legal dispute. In bespoke (B), the SRS is a working document. In product org (A), there is no client contract at all.
Q16 · Topic: Change Management

What is the FIRST step in the Requirements Change Management process?

  • AUpdate the SRS immediately
  • BEstimate the cost of the change
  • CProblem analysis and change specification
  • DImplement the change in code
✅ C. Stage 1 is Problem Analysis — validate that the change is necessary and specify it formally. Only after the change is validated and formalized can you estimate cost (B, Stage 2) or implement (D, Stage 3). Never update the SRS (A) before analysis and approval.
Q17 · Topic: NFRs

An NFR states: "The system shall be implemented using the organization's standard Java development environment." This is a:

  • AProduct NFR — Performance requirement
  • BExternal NFR — Interoperability requirement
  • COrganizational NFR — Environmental/process standard
  • DFunctional requirement
✅ C. Organizational NFR — the requirement comes from the organization's internal standards/processes, not from the product's functionality or external law. "Use Java" is a development environment standard imposed by the organization. Tricky: students confuse this with External because "Java" feels like an outside constraint — but External NFRs come from external REGULATORS or LAWS, not internal organizational standards.
Q18 · Topic: Agile RE

Which context is LEAST suitable for agile requirements engineering?

  • AA mobile app startup with rapidly changing market requirements
  • BA 4-developer team building an e-commerce website
  • CMedical device software requiring FDA regulatory approval
  • DA web-based project management tool for SMEs
✅ C. Safety-critical systems requiring regulatory approval (FDA, DO-178, IEC 62304 for medical) REQUIRE complete formal documentation. Agile's "working software over comprehensive documentation" directly conflicts with regulatory requirements. All other options are appropriate agile candidates.
Q19 · Topic: SRS Structure

The Glossary section of an SRS primarily serves to:

  • ADefine the system architecture
  • BList all system requirements in alphabetical order
  • CDefine technical terms used in the document so non-technical readers can understand them
  • DDocument the change history of the SRS
✅ C. The Glossary bridges technical and non-technical audiences — it's the key mechanism that allows the SRS to serve multiple audiences. D (change history) is in the Preface. Architecture is Section 5. Alphabetical listing of requirements would be the Index.
Q20 · Topic: Legacy Software

The PRIMARY reason organizations continue using legacy software despite its age is:

  • AThe software is still being actively developed by its original team
  • BCritical business processes depend on it and the cost/risk of replacement is too high
  • CThe software uses more advanced algorithms than modern systems
  • DRegulatory requirements mandate the use of legacy systems
✅ B. The core reason: critical business dependency + replacement risk/cost. Banks run COBOL systems from the 1970s because replacing them risks operational disruption and costs hundreds of millions. A is false (original teams are usually gone). C is false. D is occasionally a side effect but not the primary reason.
Q21 · Topic: Requirement Properties

Which word used in a requirement indicates it is MANDATORY rather than optional?

  • AShould
  • BMay
  • CShall
  • DCan
✅ C. "SHALL" = mandatory/non-negotiable. "SHOULD" = desirable but not mandatory. "MAY" and "CAN" = optional/permitted. This is IEEE/ISO standard language for requirements. Any examiner writing RE questions WILL test this.
Q22 · Topic: QFD

In QFD, a feature the customer did not ask for but which creates strong positive satisfaction when delivered is called a:

  • ANormal requirement
  • BExpected requirement
  • CExciting requirement (Delighter)
  • DPerformance requirement
✅ C. Exciting/Delighter requirements. QFD's three types: Normal (explicitly asked for), Expected (so obvious it goes unstated — causes dissatisfaction if absent), Exciting (unexpected, creates delight). D (Performance) is from Kano Model — similar concept but different terminology. Know which framework uses which term.
Q23 · Topic: Product Backlog

In agile Scrum, who is responsible for maintaining and prioritizing the product backlog?

  • AThe Scrum Master
  • BThe development team collectively
  • CThe Product Owner
  • DThe senior developer / tech lead
✅ C. The Product Owner owns, maintains, and prioritizes the backlog. This is their primary RE responsibility. Scrum Master (A) facilitates ceremonies and removes impediments — not a requirements role. The dev team (B) estimates effort but does not control priority. Tech lead (D) has no formal Scrum role for backlog.
Q24 · Topic: FAST

A key distinguishing rule of the FAST (Facilitated Application Specification Technique) meeting is:

  • AOnly technical developers are allowed to attend
  • BThe meeting is held at a neutral location and led by a facilitator who is neither developer nor client
  • CRequirements are written by the client only, then reviewed by developers
  • DThe meeting must last exactly 8 hours
✅ B. FAST's defining characteristics: neutral location (to avoid power dynamics), neutral facilitator (not developer or client — to remain unbiased). The neutral facilitator and location are specifically designed to overcome the problem of one party dominating discussions.
Q25 · Topic: Domain Requirements

Domain requirements are dangerous primarily because they:

  • AAre always technically infeasible
  • BAre often implicit — domain experts assume engineers know them, so they go unstated
  • CAlways conflict with functional requirements
  • DChange more frequently than any other requirement type
✅ B. Domain requirements are often implicit — expert knowledge that practitioners take for granted and never verbalize because "everyone in this field knows this." Engineers without domain expertise miss these requirements entirely, leading to systems that violate industry rules, regulations, or standard practices.
Q26 · Topic: Consistency Check

R-001 states "Session shall expire after 5 minutes of inactivity" and R-045 states "Users shall be able to complete complex 30-field data entry forms without re-authentication." These two requirements fail which validation check?

  • AValidity check
  • BCompleteness check
  • CConsistency check
  • DRealism check
✅ C. These two requirements directly contradict each other. Filling a 30-field form takes longer than 5 minutes → session expires mid-form → R-001 prevents compliance with R-045. This is a classic Consistency Failure. Both requirements may individually be valid (A) — the problem is their interaction.
Q27 · Topic: RE Activities

Generating test cases from requirements during the RE phase is primarily a technique for:

  • ARequirements elicitation
  • CRequirements specification
  • BRequirements validation
  • DRequirements management
✅ C — Requirements Validation. Test case generation during RE is a validation technique — if you cannot write a test case for a requirement, it fails the verifiability check. This catches unverifiable requirements BEFORE any code is written. Don't confuse with testing (which comes after coding).
Q28 · Topic: Requirement Cost

According to Boehm's Law (cost escalation principle), a requirements defect found AFTER deployment costs approximately how much more to fix than if found during RE?

  • A2–5 times more
  • B10–20 times more
  • C50–100 times more
  • D100–200 times more
✅ D. 100–200 times more. This is the key economic argument for RE investment. During RE = 1×. During design = 3–5×. During coding = 10×. During testing = 50×. After deployment = 100–200×. This is THE most cited statistic in RE — it's almost certain to appear in an exam.
Q29 · Topic: RE Difficulty

The "know-it-when-I-see-it" problem in requirements engineering refers to:

  • AEngineers knowing requirements before clients state them
  • BStakeholders being unable to articulate what they need but recognizing a good solution when they see it
  • CThe ability to identify requirements by looking at competitor systems
  • DThe technique of using prototypes to discover requirements
✅ B. Stakeholders cannot fully articulate their requirements upfront — they only recognize whether a solution is right when they see it. This is WHY prototyping is valuable: it gives stakeholders something to react to, surfacing requirements that they couldn't have stated beforehand.
Q30 · Topic: Types of NFR

MTTF (Mean Time To Failure) is a metric used to measure which NFR property?

  • APerformance
  • BReliability
  • CUsability
  • DPortability
✅ B. Reliability. MTTF = how long the system runs before failing. Reliability = probability of system working correctly over time. Performance is measured in transactions/second or response time. Usability in training time or error rate. Portability in % target-dependent statements.
Q31 · Topic: RE vs Design

Which of the following is a DESIGN decision, NOT a requirement?

  • A"The system shall store all customer transaction records permanently"
  • B"The system shall respond to search queries within 2 seconds"
  • C"The system shall use a PostgreSQL relational database for data storage"
  • D"Only authenticated users shall access patient records"
✅ C. Specifying PostgreSQL is a DESIGN decision — it dictates HOW data is stored. Requirements must be solution-independent. The WHAT is "store records permanently" (A). The design team decides HOW (PostgreSQL vs MongoDB vs Oracle). Including technology choices in requirements prematurely constrains architecture.
Q32 · Topic: Scenarios

A scenario in requirements engineering MUST include which of the following elements?

  • AUML class diagram
  • BInitial system state, normal flow, exceptions, and final state
  • CCost estimate and timeline
  • DStakeholder signatures
✅ B. A complete scenario must have: (1) initial state, (2) normal event flow, (3) what can go wrong (exceptions), (4) concurrent activities, (5) final state. Without exceptions, the scenario is incomplete — real systems must handle failure cases. UML diagrams (A) are graphical notations, not part of scenario structure.
Q33 · Topic: Kano Model

In the Kano Model, a "Basic" (Must-Be) feature is characterized by:

  • ACreating high satisfaction when present and no impact when absent
  • BLinear relationship: more of it = more satisfaction
  • CTaken for granted when present but causing strong dissatisfaction when absent
  • DUnexpected features that create delight when present
✅ C. Basic features: assumed by users (nobody thanks you for them), but their ABSENCE creates strong dissatisfaction. Example: brakes on a car. A is wrong — Basic features don't create satisfaction when present. B describes Performance features. D describes Excitement/Delighter features.
Q34 · Topic: Requirement Completeness

Which technique is MOST effective for checking requirements completeness?

  • AChecking each requirement for the "shall" keyword
  • BTracing requirements to all stakeholder viewpoints and all user scenarios to identify gaps
  • CCounting the total number of requirements
  • DComparing the SRS word count against industry benchmarks
✅ B. Completeness checking requires systematically verifying: for every stakeholder group, for every usage scenario, is there a corresponding requirement? Gaps appear when a scenario has no requirement covering it. A (checking "shall") tests language, not completeness. C and D are meaningless metrics for completeness.
Q35 · Topic: RE for Safety-Critical Systems

The Requirement Traceability Matrix (RTM) is legally required in safety-critical systems because:

  • AIt makes the system faster
  • BIt provides evidence to regulators that every requirement has been implemented and tested
  • CIt is required by the Agile Manifesto
  • DIt replaces the need for testing
✅ B. Regulators (FDA, DO-178, IEC 62304) require evidence that every safety requirement was implemented and verified. The RTM provides this audit trail: REQ → DESIGN → CODE → TEST CASE. Without it, the regulator cannot approve the system. C is wrong — Agile Manifesto actually de-emphasizes documentation.
Q36 · Topic: Backlog Grooming

Backlog grooming (refinement) primarily involves:

  • ADeleting old user stories from the backlog
  • BWriting new user stories for the next sprint during the sprint itself
  • CRefining, estimating, splitting, and reprioritizing backlog items before upcoming sprints
  • DReviewing completed features with the client
✅ C. Grooming = adding detail, estimating effort, splitting large stories, and reordering. D describes the Sprint Review. A is wrong — stories aren't deleted, they're reprioritized or moved to "Won't Have." B is wrong — grooming happens BEFORE sprints, not during.
Q37 · Topic: Supplier Organization

A software company builds a core HR system and deploys it for 5 different companies, each with custom modules for their specific HR processes. The requirements for the common base are:

  • AVariant requirements
  • BClient-specific requirements
  • CCore requirements
  • DDomain requirements
✅ C. Core requirements = shared by ALL clients, implemented once. Variant requirements (A) = client-specific, customized per client. This core/variant split is the fundamental architectural challenge of supplier organizations serving multiple clients.
Q38 · Topic: Architecture & Requirements

A requirement stating "System shall handle 500,000 concurrent users" is an example of an architecturally significant requirement because:

  • AIt is a functional requirement
  • BIt eliminates entire categories of architectural options and forces specific design choices
  • CIt is the most expensive requirement to implement
  • DIt was requested by the most important stakeholder
✅ B. An architecturally significant requirement is one that constrains or drives the architecture. 500,000 concurrent users eliminates single-server monolithic architecture completely — forces distributed systems, load balancers, caching layers. Not all requirements affect architecture equally; ASRs are the ones that do.
Q39 · Topic: Ethnography

Ethnography CANNOT discover which type of requirements?

  • AImplicit/tacit requirements
  • BCooperation and awareness requirements
  • CHigh-level strategic business requirements
  • DWorkflow and process requirements
✅ C. Ethnography observes WORKERS in their environment — it discovers what they DO, not why the organization exists. Strategic business requirements (expansion plans, revenue targets, competitive strategy) come from executives, not from observing daily work. Ethnography is excellent for A, B, and D.
Q40 · Topic: Enduring vs Volatile

Which of the following is most likely an ENDURING (stable) requirement?

  • A"VAT rate for all taxable items shall be 17%"
  • B"System shall support biometric login using fingerprint"
  • C"The system shall maintain complete and accurate patient medical records"
  • D"System shall integrate with the WhatsApp Business API for notifications"
✅ C. "Maintain complete patient medical records" is enduring — it reflects the core purpose of a hospital system and will never change as long as the hospital exists. A is mutable (government changes tax rates). B is volatile (biometric technology evolves, APIs change). D is volatile (WhatsApp API terms change).
Q41 · Topic: Change Request

Which of the following changes to a baselined SRS should be processed through the formal change management process?

  • AOnly changes requested by the client
  • BOnly legally mandated regulatory changes
  • CALL changes, regardless of source or urgency
  • DOnly changes that affect the project timeline
✅ C. ALL changes must go through formal change management — regardless of size, source, or urgency. "It's mandatory by law" does not exempt a change from impact analysis. "It's just a small fix" has caused catastrophic cascading failures in history. The process exists precisely for ALL changes.
Q42 · Topic: RE Failure

According to the Standish Group's CHAOS Report, which factor is consistently cited as a top cause of software project failure?

  • APoor programming language choice
  • BIncomplete or poorly specified requirements
  • CUse of open-source software components
  • DInexperienced programmers
✅ B. The CHAOS Report consistently ranks incomplete/unclear requirements and lack of user involvement as the #1 and #2 causes of project failure — not technical factors like programming language or developer experience. This is the statistical evidence that justifies RE as a discipline.
Q43 · Topic: Sprint Planning

In agile Scrum, what determines HOW MANY user stories are selected for a sprint?

  • AThe Product Owner's preferences
  • BThe team's velocity (capacity based on past sprints)
  • CThe number of developers on the team
  • DThe client's deadline
✅ B. Velocity — the team's measured capacity to complete story points per sprint based on historical performance. Selecting more stories than velocity allows creates overcommitment and sprint failure. The PO (A) prioritizes WHICH stories go first, but doesn't control HOW MANY fit. Team size (C) influences velocity but isn't the direct selector.
Q44 · Topic: Tricky Definition

The statement "Requirements are not discovered — they are negotiated" implies:

  • AAll requirements must be agreed upon by majority vote
  • BRequirements emerge from discussion and compromise among stakeholders with different perspectives
  • CEngineers have equal say in requirements as clients
  • DRequirements should never be changed once agreed
✅ B. No single stakeholder has the complete picture. Requirements only become complete and consistent through structured discussion, surfacing conflicts, and finding workable compromises. "Discovered" implies requirements pre-exist waiting to be found — the truth is they are constructed through negotiation.
Q45 · Topic: RE Document

Section 8 ("System Evolution") of the SRS is primarily intended for:

  • AEnd users learning the system
  • BTesters writing test cases
  • CSystem architects and maintenance engineers who need to understand anticipated changes and constraints
  • DProject managers tracking budget
✅ C. Section 8 describes anticipated changes (known volatile areas) and existing constraints/limitations. This guides architects in designing for future flexibility and helps maintenance engineers understand where changes are expected. It tells them: "Here's where the system will need to evolve — design for it now."
Q46 · Topic: Ambiguity

Which of the following requirements is CORRECTLY written?

  • A"The system should provide good performance under load"
  • B"The system shall be easy for users to learn"
  • C"The system shall process 1000 transactions per second with less than 500ms average response time under normal load of up to 5000 concurrent users"
  • D"The system must be modern, intuitive and scalable"
✅ C. C is the only verifiable, measurable, precise requirement. It passes all five validation checks: valid, consistent, complete, realistic, and verifiable (test case: simulate 5000 users, measure TPS and response time). A uses "should" (optional) and "good" (unmeasurable). B fails verifiability. D has 3 unverifiable adjectives.
Q47 · Topic: Prototyping

A prototype built only for requirements elicitation, then discarded, is called:

  • AEvolutionary prototype
  • BThrowaway (Exploratory) prototype
  • CIncremental prototype
  • DVertical prototype
✅ B. Throwaway/Exploratory prototype — built quickly to elicit requirements, then discarded. NOT intended to become the final system. Evolutionary prototype (A) grows into the final system. The danger of throwaway: clients see it and say "just finish this!" — then you're stuck with a low-quality foundation.
Q48 · Topic: JAD

JAD (Joint Application Development) was originally introduced by:

  • AMicrosoft
  • BIBM
  • CIEEE
  • DGoogle
✅ B. IBM. JAD was developed by IBM in the late 1970s as a structured methodology for involving users directly in system development. It became the formal framework behind collaborative requirements gathering meetings. Quick fact: FAST (Facilitated Application Specification Technique) is related but was developed by Edward Yourdon.
Q49 · Topic: Product Org RE

In a product organization (e.g., building a SaaS app for the general market), requirements are treated as:

  • ALegal contracts with specific customers
  • CImmutable specifications that cannot change
  • BPredictions about market needs validated through research, analytics, and user feedback
  • DDomain requirements derived from regulatory standards
✅ C. Product organizations have no named client to write a contract with (A). Requirements are predictions/hypotheses about what the market needs, validated through research, A/B tests, usage analytics, and user feedback cycles. If the prediction is wrong, users don't adopt the product — there's no legal remedy.
Q50 · Topic: Big Picture / Synthesis

Which statement BEST summarizes the relationship between RE quality and project success?

  • AGood coding can compensate for poor requirements
  • BRE is only critical for large government projects
  • CPoor requirements cause the system to be built correctly for the wrong purpose, which no amount of good coding can fix
  • DTesting is more important than requirements because it catches all RE errors
✅ C. This is the fundamental insight of RE. A well-coded system built on wrong requirements is a perfectly functioning wrong solution. Testing (D) can only verify that the system matches its requirements — if the requirements are wrong, testing passes while the system still fails the user. RE is the one activity that cannot be compensated for by any downstream quality effort.
